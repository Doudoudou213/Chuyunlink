# 楚韵链迹：故事与链迹 V2 最终开发计划

更新日期：2026-08-23  
状态：已定稿，作为后续主开发与视觉设计的共同依据  
适用范围：网页、微信小程序及未来全国化内容体系

## 实施进度（2026-08-24）

P0 第一批已在本地完成：

- 新增 `story_claims` 与 `story_claim_logs`，事实原句可绑定一份或多份已确认来源；
- 只允许引用所选章节原有来源，且会再次检查资源、链迹和投稿公开状态；
- 用户故事正文支持句末“依据”入口，手机端以底部抽屉展示原始材料和贡献者；
- 故事下方新增最多 5 个节点的轻量“朱漆链迹”，直接说明材料为什么有关；
- 管理员可在原故事工作台确认、标记待补、标记争议或停用事实依据；
- 旧故事没有事实记录时保持原样，不迁移、不覆盖、不删除已有数据。

尚未进入本批：章节级局部修订、资料征集任务、贡献影响力与行为统计、多模态材料正式入链。

## 1. 最终目标

将当前“审核投稿—绑定资源—生成带来源短故事”的闭环，升级为一个可信、好读、可继续补充的文化叙事系统。

用户端的核心体验保持简单：

1. 在投稿下方直接读到一段简短、有吸引力的故事；
2. 看见 3—5 个关键链迹节点，理解“这些材料为什么有关”；
3. 感兴趣时再展开句级依据、原始材料和完整链迹；
4. 发现资料缺口时，可以直接补充对应材料；
5. 新证据出现后，只修订受影响的事实和章节，不重写整篇故事。

系统目标不是建立一个庞大但难以使用的知识图谱，也不是让 AI 自动生产文化结论。原始资料永久保留，公开事实必须有证据，候选关系和故事必须经过人工终审。

## 2. 当前基础

目前已经具备：

- `submissions`：保存用户原始投稿、授权、地点和审核状态；
- `resources`：保存统一文化资源；
- `story_evidence_links`：保存已确认的投稿—资源证据关系；
- `ai_link_candidates`：保存 AI 提出的未公开候选关系；
- `story_chains`：保存带来源故事、章节、草稿、公开版本和历史版本；
- `storyWorker`：只读取确认关系生成结构化故事草稿；
- `materialWorker`：具备模拟 OCR 和受控腾讯 OCR 适配器；
- 管理员关系确认、故事校读、发布、归档和日志；
- 投稿内短故事、来源查看、链迹关系、补充材料和纠错反馈；
- 故事生成前后质量门槛、材料版本递增和更新提醒。

现阶段主要限制：

- 关系仍以“投稿—资源”为主，多跳语义不足；
- 来源主要绑定章节，尚未细化到关键事实或句子；
- 链迹视图偏关系展示，缺少清楚的阅读路径；
- 新材料通常触发整篇故事更新，缺少局部修订；
- OCR 校对结果尚未进入正式故事输入；
- 缺少定向资料征集、贡献影响力和阅读效果指标；
- 主题链尚未形成稳定的编辑与发布流程。

## 3. 对新增建议的取舍

### 3.1 直接采纳

- 多跳关系链，但采用有限节点类型和受控关系词表；
- 管理员策划的主题链迹；
- 句级或事实级来源入口；
- 结构化事实断言与证据状态；
- 章节级局部修订；
- 故事版本变化说明；
- “为什么值得一起看”的惊奇连结；
- 面向明确资料缺口的定向征集；
- 投稿被故事采用后的贡献归因和通知；
- 完读、来源展开、补充转化等最小必要埋点。

### 3.2 调整后采纳

#### 事实断言树

不采用严格的树结构，改为“事实断言表”。一个事实可能同时得到多份证据支持，也可能存在相互冲突的证据，图或列表比树更符合实际。

#### 图片纹样向量搜索

只把结果标记为“视觉相似候选”，不能称为“同源”。相似度数字只供管理员排序，不向普通用户呈现为历史结论。

#### 资料缺口悬赏

用户端名称采用“资料征集任务”或“共同补全”，避免所有文化贡献都被游戏化。任务和积分必须由管理员确认；AI 只能提出任务草稿，不能自动承诺或发放积分。

#### 版本 Diff

普通用户默认只看一句清楚的修订摘要；完整逐句 Diff 放在“修订历史”展开层。管理员后台保留完整变化对比。

#### 原始材料预览

句级来源可展示投稿缩略图、文字节选或音频片段，但必须遵循用户授权、隐私状态和公开范围。不能因为故事引用而自动公开原始高清文件或完整录音。

### 3.3 暂缓

- 大规模视觉向量库和全库纹样检索；
- 音频自动时间码引用；
- 视频抽帧和跨模态相似搜索；
- 面向普通用户的完整大型思维导图；
- AI 自动创建并发布全国主题链。

暂缓原因是成本、授权、标注质量和误判风险较高。先完成事实级引用、局部修订和 OCR 闭环，再逐步启用。

### 3.4 明确放弃

- 用单一相似度直接判定纹样“同源”；
- AI 自动确认历史关系或自动发布故事；
- 新材料到来后覆盖旧故事和原始投稿；
- 自动生成高额积分悬赏并直接结算；
- 在用户首屏展示复杂全量图谱；
- 使用同一个生成模型给自己的故事做最终裁决。

## 4. V2 产品结构

### 4.1 用户端采用“一卡三层”

#### 第一层：直接阅读

投稿卡片下展示：

- 短标题；
- 80—160 字核心故事；
- “已人工校读”状态；
- 一条 3—5 节点的关键链迹；
- 一个主要操作：“补充这段链迹”。

#### 第二层：理解关系

用户展开后看到：

- 每两个节点之间的“为什么有关”；
- 关键事实后的 `[依据 1]`；
- 简短来源卡片；
- 当前仍缺少的资料。

#### 第三层：深度追溯

继续展开后才能看到：

- 完整链迹网络；
- 时间线和地点；
- 原始材料的授权预览；
- 修订历史；
- 纠错与补充记录。

这样既保持入口简单，又保留研究与追溯深度。

### 4.2 管理员端采用“五步工作台”

1. 审核原始投稿；
2. 确认实体和关系候选；
3. 审核事实断言及其证据；
4. 校读故事和局部修订建议；
5. 发布版本、征集任务或主题链。

每一步都必须显示“机器建议”和“人工确认”的区别。

## 5. 数据模型 V2

采用增量扩展，不删除现有集合。

### 5.1 `story_entities`

表示可复用节点：

- `submission`
- `detail_or_motif`
- `heritage_object`
- `building_or_site`
- `person_or_group`
- `event`
- `text_or_archive`
- `craft_or_practice`
- `time_period`
- `place`

核心字段包括：标准名称、别名、类型、行政区划、时间范围、关联资源、公开状态和审计信息。节点类型保持全国通用，不写死湖北专属分类。

### 5.2 `story_relations`

保存实体之间的正式关系。第一版只允许有限关系：

- `located_at`
- `documents`
- `depicts`
- `uses_craft`
- `associated_with_person`
- `associated_with_event`
- `mentioned_in`
- `changed_over_time`
- `visually_similar_to`
- `influenced_or_transmitted_to`

其中 `visually_similar_to` 只表示外观相似；`influenced_or_transmitted_to` 必须有人工确认的文献或现场证据。

每条关系必须包含证据引用、状态、提出者、审核者和置信说明。旧 `story_evidence_links` 继续作为投稿—资源关系来源，由兼容层映射到新关系模型。

### 5.3 `story_claims`

保存故事中的关键事实，而不是只保存整段正文：

- 事实正文；
- 所属故事、版本和章节；
- 对应句子或字符范围；
- 支持证据 ID；
- 反对或冲突证据 ID；
- 状态：`supported`、`disputed`、`needs_evidence`、`retired`；
- 人工确认信息；
- 受材料版本影响的范围。

公开故事中的重要年代、人物、技艺、因果关系和数量必须对应至少一条已确认事实。

### 5.4 `story_themes`

保存跨地点、跨时代专题链：

- 主题名称和导语；
- 编辑选定的核心节点；
- 节点顺序和分组；
- 关键问题；
- 使用的故事与证据；
- 发布状态和版本；
- 适用地区和时间范围。

AI 可以建议主题和节点排序，但只有管理员可以正式创建、调整和发布。

### 5.5 `story_gap_tasks`

保存资料征集任务：

- 缺口类型；
- 对应故事、章节、事实或实体；
- 所需材料和拍摄/录音要求；
- 地点与有效期；
- 积分规则；
- 管理员审批状态；
- 投稿数量、采纳状态和结算记录。

积分只在投稿审核通过且满足任务条件后，由服务端结算。

## 6. 故事生成与修订流程

### 6.1 新故事

```text
已确认材料
→ 生成证据卡片
→ 提取事实断言候选
→ 管理员确认或修正
→ 生成故事提纲
→ 生成短故事草稿
→ 规则校验来源、隐私、数字和套话
→ 管理员校读
→ 发布版本
```

### 6.2 新材料进入后的局部修订

```text
新投稿审核通过
→ 更新材料版本
→ 判断影响的实体、关系和事实
→ 定位受影响句子或章节
→ 生成局部修改建议
→ 展示修改前后和新增依据
→ 管理员确认
→ 发布新版本，保留旧版本
```

默认禁止模型改动未受影响章节。若证据导致故事主线发生变化，管理员可以明确选择“重新编排整篇故事”。

### 6.3 来源交互

移动端以点击为主，不依赖悬停。点击 `[依据 1]` 后打开底部抽屉，显示：

- 来源类型和公开昵称；
- 经授权的缩略图或局部图；
- 文字节选；
- 经确认的音频时间段；
- 审核状态；
- “查看完整来源”入口。

## 7. 分阶段实施

### 阶段 0：基线与指标定义

工作内容：

- 冻结现有故事公开响应作为 V1 兼容基线；
- 记录当前故事数量、来源数量、版本数量和反馈数量；
- 定义埋点口径与隐私边界；
- 增加 V2 功能开关，默认关闭。

完成条件：关闭 V2 时，线上现有故事、评论、补充和管理员流程完全不变。

### 阶段 1：事实级引用与轻量链迹

工作内容：

- 新增 `story_claims`；
- 为现有代表故事人工补录关键事实和证据；
- 扩展公开接口，返回脱敏的事实引用；
- 投稿卡片增加 3—5 节点轻量链迹；
- 增加“为什么有关”和来源底部抽屉；
- 管理端增加事实确认界面。

试点范围：先选择 3—5 个材料较完整的文化资源，不批量迁移全部内容。

完成条件：每条试点故事的关键事实均可回到真实来源，手机端不增加新的顶层入口。

### 阶段 2：局部修订与版本差异

工作内容：

- 建立材料—事实—句子—章节影响映射；
- `storyWorker` 支持局部修订任务；
- 管理端显示修改前后、原因和新增依据；
- 用户端显示简短修订摘要；
- 完整 Diff 和日志按需展开。

完成条件：增加一份只影响第三章的材料时，前两章文本和引用保持不变。

### 阶段 3：多跳实体与关系

工作内容：

- 新增 `story_entities` 和 `story_relations`；
- 建立有限节点类型、关系词表和中文显示文案；
- 增加实体去重、别名和行政区划字段；
- AI 只在影子模式提出实体与关系候选；
- 管理员确认后才能进入公开链迹；
- 用户端提供简化路径，完整网络继续放在深层展开中。

完成条件：支持“投稿→纹样→文物→文献/人物”的多跳路径，并且每一步均有证据和审核记录。

### 阶段 4：资料征集、贡献归因与最小埋点

工作内容：

- 新增 `story_gap_tasks`；
- 管理员根据 `needs_evidence` 事实发布征集任务；
- 采集页接收预设故事、章节、地点和材料类型；
- 审核通过后服务端结算积分；
- 个人主页显示投稿被采用次数、进入故事数量和公开阅读影响；
- 向贡献者发送采用、修订和发布通知；
- 接入最小埋点。

首批指标：

1. 故事展开率；
2. 有效阅读率，而不是单纯停留时间；
3. 来源展开率；
4. 轻量链迹节点点击率；
5. “补充这段链迹”进入与审核通过率；
6. 资料征集任务完成率；
7. 用户纠错被采纳率。

完成条件：所有影响力数字来自服务端真实聚合；私密投稿、用户 UID 和未公开昵称不进入统计响应。

### 阶段 5：管理员确认后的多模态材料

按风险从低到高实施：

1. 接通已校对 OCR 文本进入事实候选；
2. 增加碑刻图片增强预览，但永远保存原图，不覆盖原始文件；
3. 接入音频转写和人工确认的时间码；
4. 小规模试验图像纹样向量候选；
5. 最后评估视频抽帧。

完成条件：故事只能读取管理员标记为可用的分析结果；撤回授权后停止新处理，并按授权规则处理派生材料。

### 阶段 6：主题宏链与全国化

工作内容：

- 管理端提供主题链编辑器；
- 支持跨省、跨年代、跨人物选择节点；
- AI 提供主题候选、章节顺序和缺口建议；
- 编辑确认后发布专题页；
- 专题页以故事为主，地图、时间线和完整链迹按需展开；
- 建立全国通用行政区划、资源类型和别名规范。

首批主题应选择证据充足的小范围试点，不追求一次覆盖全国。例如先做“凤鸟纹样的区域传播”或“长江沿线古城墙营造与防洪”。

完成条件：主题链中的每个关键断言都有来源；跨地区关系不能仅依靠视觉相似度成立。

## 8. 安全与内容边界

- 原始投稿、原始文件和历史故事版本不物理覆盖；
- 新集合禁止客户端直接读写，统一通过云函数鉴权和脱敏；
- AI 密钥、OCR 密钥和管理员信息只保存在云函数环境变量；
- 公开接口不返回 UID、私有 fileID、管理员 UID 和内部模型信息；
- 未授权图片、完整录音和个人信息不能因故事引用而自动公开；
- AI 只能生成候选、提纲和草稿，不能确认事实、发布故事或结算积分；
- 矛盾资料应标记为“存在不同记录”，不能由模型静默选择一种说法；
- 全国化后需要支持地区管理员权限范围，避免所有管理员都能修改全部地区内容。

## 9. 测试与验收

每个阶段至少包含：

- 数据契约测试；
- 云函数权限和脱敏测试；
- 旧数据兼容测试；
- 故事来源不可伪造测试；
- 版本和局部修订测试；
- 积分重复结算与并发测试；
- 授权撤回测试；
- 手机 390px、平板 768px、桌面 1440px 视觉验收；
- CloudBase 部署前统一构建检查；
- 代表资源的管理员人工验收。

生产发布采用功能开关和少量资源试点。任何数据迁移先生成只读预览，不直接覆盖线上数据。

## 10. 最终优先级

### P0：下一轮立即开发

1. `story_claims` 事实级引用；
2. 投稿内 3—5 节点轻量链迹；
3. “为什么有关”和移动端来源抽屉；
4. 管理员事实确认；
5. 局部修订和修订摘要。

### P1：P0 稳定后开发

1. 多跳实体和受控关系；
2. 资料征集任务；
3. 贡献影响力与通知；
4. 最小埋点与质量复盘；
5. OCR 确认结果进入故事。

### P2：内容和运营稳定后开发

1. 音频时间码；
2. 纹样视觉相似候选；
3. 主题宏链；
4. 全国专题与地区管理员；
5. 路线讲解和语音版本。

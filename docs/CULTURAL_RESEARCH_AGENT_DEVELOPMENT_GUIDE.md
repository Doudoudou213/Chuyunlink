# 楚韵链迹：文化研究智能体开发手册

更新日期：2026-09-06
状态：已确认，作为后续智能体、链迹、故事与多模态开发的共同依据  
适用范围：CloudBase 网页端、微信小程序、管理员端及未来全国化内容体系

## 0. 先看这一页

楚韵链迹要建设的不是普通聊天机器人，而是一个在后台工作的 **“证据约束文化研究智能体”**。

它接收已审核且已授权的投稿，自动完成：

```text
理解投稿
→ 检索已有资源
→ 提取实体并查重
→ 提出多跳关系候选
→ 绑定真实来源
→ 判断风险和资料缺口
→ 生成短故事或局部修订候选
→ 交由规则或管理员确认
```

核心原则：

1. AI 负责理解、检索、比较和提出候选，不负责确认历史事实；
2. 低风险基础关系由确定性程序随投稿审核一起建立，不增加管理员操作；
3. 管理员只处理少量中高风险候选，不成为数据录入员；
4. 正式故事和链迹中的重要判断必须能回到真实来源；
5. 用户端不新增复杂“AI入口”，智能能力自然出现在投稿故事、链迹和共同补全中；
6. 所有任务有调用上限、缓存、日志、暂停和恢复能力，费用必须可预测；
7. 先积累管理员修改数据，再考虑微调自己的小模型。

## 1. 产品定位与创新点

项目不以“AI批量生成文化介绍”为目标。真正的创新定位是：

> 将公众提交的零散文化材料，转化为有证据、有关系、有版本、可继续补充的文化记忆网络。

重点能力包括：

- **证据约束**：区分已确认事实、合理推测、视觉相似、资料不足和争议记录；
- **多跳链迹**：支持“投稿细节 → 纹样 → 文物/建筑 → 人物/事件 → 古籍/档案 → 当代技艺”；
- **增量更新**：新资料只影响相关事实、关系和章节，不重写整篇故事；
- **缺口驱动共创**：智能体发现资料不足后，生成定向征集任务草稿；
- **贡献归因**：投稿被故事采用、帮助补全链迹时，记录贡献、通知和积分；
- **持续学习**：管理员的确认、修改和驳回结果沉淀为评测集与未来训练数据。

LangGraph、Dify或任何大模型都只是实现工具，不是项目创新本身。

## 2. 当前已有基础

现有系统已经具备：

- `submissions`：用户原始投稿、授权、位置与审核状态；
- `resources`：统一文化资源；
- `story_evidence_links`：投稿与资源之间的正式证据关系；
- `story_entities`：纹样、文物、建筑、人物、事件、古籍、技艺、时代和地点等实体；
- `story_relations`：经过确认、带来源的正式多跳关系；
- `story_claims`：故事关键事实与句级来源；
- `story_chains`：故事草稿、公开版本与修订历史；
- `story_gap_tasks`：定向资料征集任务；
- `story_contributions`：采用记录、通知与额外积分；
- `storyWorker`：带质量门槛和来源约束的故事草稿生成；
- `materialWorker`：模拟OCR与受控腾讯OCR适配器，真实OCR目前默认关闭。

智能体建设应增量复用这些数据，不复制、不覆盖、不迁移原始投稿。

### 2.1 第一阶段实施状态（2026-08-28）

第一阶段“影子模式”已完成本地代码与自动化验证，尚未部署、尚未开启真实模型调用：

- 新增独立 `storyAgentWorker`，与故事生成、管理员审核和用户端界面分离；
- 只接收“审核通过 + 用户明确授权 + 文字达到最低长度”的投稿；

## 3. 智能来自哪里

智能体由四部分共同组成：

1. **大模型**：理解文字、比较材料、提出实体和关系候选；
2. **业务工具**：检索资源、查重、读取证据、保存候选、生成征集任务；
3. **确定性规则**：鉴权、隐私、关系词表、来源有效性、费用和状态检查；
4. **持久状态**：记录任务进行到哪一步，失败后可继续，等待人工确认后可恢复。

当前模型来源为腾讯云 TokenHub 的 Hy3。密钥只保存在云函数环境变量。模型通过兼容接口调用，后续可以替换为DeepSeek、Qwen、GLM或自部署模型，不能把业务流程锁死在单一模型上。

LangGraph只负责步骤编排、暂停、恢复和人工介入，不提供模型智能。第一版优先采用CloudBase持久任务状态机；当流程分支、并行步骤和人工中断明显增加时，再引入LangGraph JS，并保持每个节点的输入输出契约不变。

- 腾讯云TokenHub计费：<https://cloud.tencent.com/document/product/1823/130055>

## 4. 总体架构

新增独立云函数 `storyAgentWorker`，不要继续把智能体逻辑堆入 `storyWorker`。

```text
投稿审核通过
   ↓
storyAgentWorker 创建异步任务
   ↓
规则预处理 → 资源检索 → 模型提取 → 实体去重
   ↓
来源校验 → 关系候选 → 风险分级 → 缺口建议
   ↓
低风险确定性结果随审核确认 / 中高风险进入批量工作台
   ↓
确认后写入 story_entities、story_relations、story_claims
   ↓
storyWorker 生成或局部修订故事
```

推荐新增集合：

- `story_agent_jobs`：任务、状态、输入指纹、模型和预算；
- `story_agent_steps`：每一步开始、完成、失败和重试记录；
- `story_agent_candidates`：未公开实体、关系、事实和缺口候选；
- `story_agent_reviews`：管理员的通过、修改、驳回与原因；
- `story_agent_usage_daily`：每日调用、Token和费用估算；
- `story_agent_evaluations`：离线评测与版本比较。

候选记录与正式记录必须分离。只有确认后的结果才能进入现有正式集合。

## 5. 第一版任务流程

### 5.1 触发条件

只有同时满足以下条件才创建任务：

- 投稿已审核通过；
- 用户已明确授权AI分析；
- 投稿尚无相同输入指纹的已完成任务；
- 当日调用量与Token预算未超限；
- 投稿文本达到最低有效信息要求。

### 5.2 执行节点

1. `normalize_submission`：清理输入，只保留业务必要信息；
2. `retrieve_context`：检索同地区、同类型和关键词相关资源；
3. `extract_candidates`：模型输出结构化实体、关系和缺口；
4. `resolve_entities`：按名称、别名、地区、时间和资源进行查重；
5. `ground_evidence`：校验每条候选使用的来源是否真实、已审核、仍有效；
6. `classify_risk`：根据关系类型、证据数量和冲突情况分级；
7. `persist_candidates`：保存候选，不进入公开接口；
8. `await_review`：需要人工判断时暂停；
9. `commit_confirmed`：确认后写入正式实体和关系；
10. `suggest_story_update`：只提出新故事或局部修订任务，不自动发布；
11. `suggest_gap_task`：资料不足时生成征集任务草稿，不自动承诺积分。

### 5.3 模型输出契约

模型必须返回经过Schema校验的JSON，禁止自由文本直接入库：

```json
{
  "entities": [
    {
      "temporaryId": "entity_1",
      "name": "凤鸟纹",
      "type": "detail_or_motif",
      "summary": "投稿花窗中可辨认的凤鸟形纹样"
    }
  ],
  "relations": [
    {
      "from": "entity_1",
      "toResourceId": "hubei-museum",
      "type": "visually_similar_to",
      "reason": "两者均呈现展开双翼的凤鸟轮廓",
      "evidenceLinkIds": ["story_xxx"],
      "risk": "medium"
    }
  ],
  "missingEvidence": [
    {
      "type": "dating_evidence",
      "request": "需要建筑年代或修缮记录"
    }
  ]
}
```

程序必须拒绝：不存在的来源、非法关系类型、自相矛盾的实体编号、未授权材料和超长输出。

## 6. 管理员减负与风险分级

### A级：确定性自动关系

由程序根据已确认业务字段建立，不依赖AI推断。例如投稿记录对象、管理员已选择的资源绑定和明确定位。它们随原投稿审核一次确认，不增加新按钮。

### B级：批量确认候选

包括外观相似、可能涉及某种技艺、可能与某项记录相关等。后台合并重复候选，只显示来源、建议和风险，支持批量通过或驳回。

### C级：单独人工判断

包括历史传播、人物影响、事件因果、跨时代继承、资料冲突和主题链关键结论。必须展示支持与反对证据，不允许批量自动发布。

### D级：证据不足

不建立正式关系，转为“共同补全”任务草稿。任务内容、积分和有效期由管理员确认。

目标不是零人工，而是让管理员只处理少量有文化判断价值的内容。

## 7. 成本控制

当前Hy3公开价格为输入1元/百万Token、输出4元/百万Token、缓存输入0.25元/百万Token，最终以腾讯云控制台为准。

第一版建议默认限制：

- 每个任务最多2次模型调用；
- 单次只检索最相关的少量资源，不发送全库；
- 单任务输入和输出均设硬上限；
- 每日最多20次调用、20万Token，与现有AI安全基线一致；
- 相同输入指纹、模型和提示版本命中缓存；
- 失败最多重试1次，超时后进入人工重试队列；
- 先用普通程序做格式、地理、重复和权限检查；
- 新材料只处理增量，不重新分析整篇故事；
- 后台展示当日调用、Token、缓存命中和估算费用；
- 默认不开启资源耗尽后无限后付费。

按输入5000 Token、输出1500 Token估算，Hy3一次约0.011元；一份投稿调用两次约0.02元。1000份投稿的纯文本模型费用通常是几十元级，OCR、图片理解、联网搜索、CloudBase和服务器费用另计。

## 8. 自有模型与训练路线

当前不从零训练大模型。历史文化事实放在可更新数据库中，不能依赖模型参数记忆。

需要保存的训练反馈包括：

- AI原始候选；
- 管理员最终关系类型；
- 通过、修改或驳回；
- 驳回原因；
- 正确实体合并结果；
- 是否缺少证据；
- 最终故事修改差异。

训练顺序：

1. 先用API和规则运行影子模式；
2. 积累数百条高质量样本，建立固定测试集；
3. 持续比较提示词和模型版本；
4. 积累约数千条稳定标注后，评估Qwen等中文小模型的LoRA微调；
5. 小模型优先承担实体提取、关系分类、风险筛选和去重；
6. 复杂文化推理和故事写作继续使用强模型API；
7. 新模型必须通过离线评测和小流量影子测试，不能直接替换生产模型。

## 9. 用户端和管理员端原则

### 用户端

- 不增加新的顶层“AI聊天”入口；
- 故事仍直接显示在相关投稿或资源下；
- 默认只显示3—5个关键链迹节点；
- 每段关系说明“为什么有关”；
- 依据、完整网络和修订历史按需展开；
- 资料不足时提供一个主要操作“补充这段链迹”。

### 管理员端

- 首页只显示“自动完成、建议确认、高风险、证据不足”四个数字；
- 复用现有UI的按钮、卡片、弹窗、颜色、字体、圆角和间距；
- 功能开发前先同步视觉开发对话的最新提交；
- 不要求管理员手工从零创建大量实体和关系；
- 候选必须展示原始依据、AI建议、风险原因和修改入口。

## 10. 安全边界

- AI不能审核投稿、确认历史事实、发布故事、发放积分或核销兑换码；
- 未授权材料不能进入模型输入；
- 原始投稿、原图、原音频和历史版本不物理覆盖；
- 公开接口不返回用户UID、管理员UID、私有fileID、模型密钥和内部提示词；
- 视觉相似只能标记为相似，不能自动升级为同源或传播关系；
- 冲突资料要保留“存在不同记录”，不能由模型静默选择；
- 模型返回的每个来源编号必须由服务端重新验证；
- 任务需要幂等编号，重复触发不得重复调用、重复建链或重复发积分；
- 所有模型调用记录模型、提示版本、输入指纹、用量和结果状态。

## 11. 分阶段开发

### 阶段1：影子模式智能体

- 新建 `storyAgentWorker` 与任务集合；
- 只处理文字投稿；

### 阶段3：故事与缺口闭环

- 最后评估视频抽帧。

完成条件：只有人工确认可用的派生材料才能进入智能体正式输入。

### 阶段5：自有小模型

## 14. 手册复核：已知缺口与验收补充（2026-09-06）

本手册是可执行路线，不是完整性证明。现阶段更需要验证正确性和工作量，而非继续扩张模型功能。

### 14.1 来源有效与事实支持必须分开

存在且已审核的来源，只证明有这份材料，并不能证明它支持某句历史断言。当前程序能校验编号、权限、部分文本数字和结构；不能声称已经自动验证全部事实。后续把关键断言拆成 claim，记录原文片段及定位、支持/反对/不足状态，管理员可直接对照核对。无法支持的具体年代、人物因果与传承关系应删除或标为待证，不能只靠置信度放行。

### 14.2 授权撤回和资料失效需要完整传播

本轮补齐了故事生成的授权检查。剩余工作是：来源撤回、下架、合并或纠错后，定位受影响的候选、关系、故事与征集；停止新调用，将受影响内容标为待复核，并保留历史。不能因为过去曾经授权，就继续使用旧输入或宣称旧故事仍然可靠。授权中断与状态检查必须覆盖重试、缓存和发布。

### 14.3 管理员工作量应实测

先记录每 100 份投稿产生的实体、关系、缺口数量，重复率、接受/修改/驳回率，以及每份处理耗时；再决定去重、批量规则与默认折叠。暂不承诺“只需很少人工”。无已发布故事时，缺口目前不能公开；不应为了消化队列而生成低质故事。

### 14.4 上线前的具体评测

- 固定至少 30 个离线案例：正常、信息不足、来源伪造、授权撤回、冲突年代、相似但不同源、并列章节、重复点击、发布中状态变化、模型超时等。
- 权限越界、伪造来源被接受、未确认结果公开、重复发奖励：必须为 0。
- 人工逐条核查试点关键断言是否被所引材料支持；报告不支持的条数，不能把引用覆盖率当成事实准确率。
- 在单独开启调用后，先试 3—5 份资料并记录实际用量、延迟和管理员修改；不以模拟测试代替这一验收。
- 自动章节改写必须验证非目标章节逐字不变、旧版本可追溯、失败不影响线上已发布版本。

### 14.5 成本与工程边界

第 7 节价格仅是编写时的估算，上线试点以供应商当时账单和实际 Token 为准。后续需补充调用中的费用预留/结算一致性、超时恢复、暂停任务和配置告警验证。现有分页与资源读取存在数量上限，扩大到全国前需做有界分页和性能检查，不能将截断列表视为全库。

### 14.6 贡献通知应对应实际动作

当前“征集采用”走已有通知与积分流程，并不等于正文已经完成修订。后续应区分“资料被采用”“已写入发布故事”两个事件，按真实发布记录归因，避免对用户提前宣称故事已更新。

调整后的顺序：完成本地失败样本与撤回影响处理 → 少量真实候选试点 → 评估管理员耗时与费用 → 自动章节改写 → 多模态。现有功能可以逐步发布，但不把整份手册标为全部完成。

### 14.7 本地完成记录（2026-09-07）
